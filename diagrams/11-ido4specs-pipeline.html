ido4specs Pipeline

Strategic spec → reviewable technical spec, in three checkpointed phases. Each phase produces a review-worthy artifact you can inspect before continuing.

Phase 1
/ido4specs:create-spec
AI: code-analyzer (inline) + parallel Explore subagents on your codebase or integration targets
Parses the strategic spec. Detects project mode (existing / greenfield-with-context / greenfield-standalone). Explores your codebase. Synthesizes a per-capability technical canvas grounded in real file paths and patterns.
Output: Technical Canvas
~15–30 min for 30+ caps
→
Phase 2
/ido4specs:synthesize-spec
AI: technical-spec-writer (inline) — pure transform, no codebase exploration
Reads the canvas. Decomposes capabilities into right-sized tasks with effort/risk/type/AI metadata and explicit dependencies. Auto-runs structural validation against the bundled parser before returning.
Output: Technical Spec (.md)
~10–20 min
→
Phase 3
/ido4specs:review-spec & /ido4specs:validate-spec
Two layers: deterministic parser (validate) + LLM judgment (review). Plus /ido4specs:refine-spec for edits.
Independent layers cross-check the spec. Deterministic content assertions (T0–T8) catch structural or metadata issues. Qualitative review surfaces missing dependencies, calibration concerns, descriptions that aren't code-grounded.
Output: PASS / PASS WITH WARNINGS / FAIL with findings
~2–5 min per skill

Strategic Spec (input)
From ido4shape or hand-authored. Groups, capabilities with priority/risk/depends_on, cross-cutting concerns, success conditions. The WHAT, not the HOW.
Technical Canvas
Strategic context preserved verbatim + per-capability codebase analysis: relevant modules, patterns, code-level dependencies, complexity assessment, surprises uncovered during exploration.
Technical Spec
Capabilities decomposed into implementation tasks. Per task: effort (S/M/L/XL), risk (low/medium/high/critical), type, AI suitability, depends_on graph, code-verifiable success conditions, file paths.
Ingestion-ready
Plain markdown that any downstream can consume. Pipe to ido4dev for GitHub issues, or to your own ticket / PM tooling. The spec is the contract.
Phase 3
two-layer review
Layer 1 — deterministic
/ido4specs:validate-spec
Bundled parser checks structural integrity (heading patterns, ref format, metadata values, dependency graph). Then T0–T8 content assertions: descriptions code-grounded, success conditions verifiable, metadata calibrated, capability coherence. Fast, cheap, reproducible.
Layer 2 — qualitative
/ido4specs:review-spec
LLM-driven review against the spec content. Catches missing dependencies named in description text, sibling-pattern inconsistencies, hub-task identification, narrative-grade quality. Surfaces what the parser can't judge.
Refine + re-validate loop: when review-spec or validate-spec surfaces findings, /ido4specs:refine-spec applies natural-language edits (typically depends_on additions, metadata corrections, description adjustments) and re-runs the bundled parser to catch structural regressions immediately. Skill boundaries are the human checkpoints — nothing auto-progresses to the next phase.
